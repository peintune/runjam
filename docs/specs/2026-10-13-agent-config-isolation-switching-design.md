# RunJam 原生与托管配置隔离、切换设计

状态：设计已确认；Codex 第一阶段已实现，Claude/Gemini 原生切换后续接入。
日期：2026-10-13

## 1. 目标与推荐结论

将“使用本机原生 CLI”和“使用 RunJam 管理的模型”做成两种显式运行模式。
切换修改会话的启动方案，不覆盖用户配置、不删除托管模型绑定。
默认推荐沿用本机原生登录：用户已在 Codex CLI 登录 ChatGPT Pro 时，原生
模式沿用该认证；托管模式独立使用 RunJam 模型、代理和会话配置。

隔离承诺限定为：RunJam 的配置管理代码不写入本机原生配置和认证目录。
原生 CLI 运行时自身仍会刷新认证、保存会话、记录信任状态等，因此原生模式
并非文件系统只读沙盒，也不是完整的状态隔离。

若用户希望连登录与会话状态也隔离，采用独立登录方案，见第 4 节。
“原生”不是“Pro”的同义词：本机 CLI 也可能配置了 API Key 或企业网关。

## 2. 当前实现核查

| 问题 | 证据 | 后果 |
| --- | --- | --- |
| 展示优先读取历史快照 | `models_config.rs:459` 的候选顺序是快照、日期备份、当前文件 | 本机后来修改配置，UI 仍可能展示旧模型 |
| Codex 当前模型标签不反映运行状态 | `models_config.rs:575` 的解析结果直接设置 `is_current: true` | 快照默认模型被展示成“当前使用” |
| 切原生仍采用旧恢复机制 | `models_config.rs:1099` 写入本机文件；`models_cmd.rs:431` 删除模型绑定 | 用户配置可能被旧快照覆盖，切换也丢失托管选择 |
| 启动总是隔离 | `acp_client.rs:813` 对所有 Agent 设置隔离变量 | 切原生恢复的文件与启动读取的文件不一致 |
| 多会话改写同一份配置 | `agent_isolation.rs:60` 按 Agent 分目录；`session_cmd.rs:81` 在启动前写模型 | 不同会话存在模型/密钥串用风险 |
| 写配置失败后继续运行 | `session_cmd.rs:94` 只记录警告；模型不存在也回退当前配置 | 选择失败可能变成用旧模型发送 |
| 代理仍按 Agent 和模型名路由 | `proxy/mod.rs:40`、`proxy/common.rs:445` | 同名模型、不同供应商的会话不能只靠模型名隔离 |
| 推理设置是代理全局状态 | `proxy/mod.rs:48` | 一个会话的推理选择可能影响其他会话 |
| 项目技能部署覆盖同名目录 | `skill.rs:227` 删除后重写 | 仅隔离用户全局目录仍不能保证项目技能不受影响 |
| Codex 同步日志打印配置全文 | `models_config.rs:832` | 配置内的 API Key 可能被写入日志 |

上述结论来自代码静态核查。没有读取用户凭据，也没有启动真实付费推理验证。

## 3. 三种方案与取舍

1. **推荐：本机原生 + 会话隔离的 RunJam 托管。** 直接复用本机登录及原生
   MCP/技能；托管配置按会话隔离。实现成本适中，满足现有登录随时切换。
2. **完全独立：RunJam 内重新登录订阅账号。** 原生风格的订阅配置和托管配置
   都在 RunJam 数据目录中。状态隔离更强，但用户需独立登录，且本机插件、
   技能、MCP 不会自动继承；不同认证存储后端还需验证目录隔离行为。
3. **复制/链接原生目录，再覆盖模型字段。** 表面上能继承配置，实际带来认证
   刷新分叉、密钥环兼容、快照陈旧和链接误写问题，不作为默认实现方案。

第一阶段采用方案 1。方案 2 作为独立可选配置来源，不混入方案 1 的隐式行为。

## 4. 配置与登录边界

| 项目 | 本机原生模式 `native` | RunJam 托管模式 `managed` |
| --- | --- | --- |
| 配置来源 | 当前本机 CLI 配置及其配置层 | RunJam 模板 + 本次会话的明确选择 |
| Codex 根目录 | 用户原本的 `CODEX_HOME`，未设置则 `~/.codex` | `<RunJamData>/agent-runs/<runId>/codex` |
| 登录来源 | 原生 CLI 认证/系统凭据存储 | 本地代理会话凭据；上游密钥由代理管理 |
| 模型来源 | 默认原生模型或临时会话覆盖 | 明确的 RunJam `modelId` |
| 模型流量 | 原生配置决定，不经过 RunJam 模型代理 | 经 RunJam 本地代理绑定至确定的模型 ID |
| 修改本机文件 | RunJam 配置管理不修改；CLI 可保存自身状态 | RunJam 与托管子进程不以本机原生目录为配置根 |
| MCP/技能 | 默认沿用原生；RunJam 的额外项需显式选择 | 默认使用本次选择的 RunJam 扩展 |
| 权限 | 默认沿用 CLI；可选择会话临时覆盖 | 使用 RunJam 本次会话权限档位 |

Claude/Gemini 使用同样的模式契约，但配置根与认证探测由各自适配器处理；
不能假定 Codex 的登录方式、存储规则或参数能直接用于另外两个 CLI。
第一阶段交付 Codex，并对 Claude/Gemini 做兼容性核验后再启用原生切换。

原生根路径必须尊重用户自定义环境变量，不能只硬编码 HOME。`RUNJAM_HOME`
现有测试语义与“本机原生根目录”拆开，测试使用显式的假原生根路径。

原生启动不得注入 RunJam 的模型、API Key、供应商地址或托管 `.env`。
原生用户自己的环境变量默认保留；若用户显式选择“ChatGPT 订阅登录”，
则由适配器验证认证路径，并避免本次子进程被 API Key/自定义供应商接管。
清理只作用于该子进程，不修改用户 shell 环境。

不通过循环复制、软链接 `auth.json` 来共享登录；Token 刷新由 CLI 负责。
本机原生模式的登录/退出作用于共享原生账号，UI 必须清楚说明；禁止在模式
切换或卸载时自动退出该账号。完全独立模式需在独立配置根发起官方登录流程，
并验证 keyring 后端不会错误共用本机账号。

原生文件读取失败应显示缺失/解析失败；不能静默改用历史快照或托管配置。
当前配置未显式写模型时，展示“使用 CLI 默认模型”，模式仍可用。

## 5. 单一启动方案与会话隔离

增加一个后端启动方案解析入口，统一服务主窗口、宠物窗口、首次启动、重启
和恢复会话。前端发送选择，后端负责验证并生成 `ResolvedLaunchPlan`。

建议输入 `LaunchSelection`：

- `configMode: native | managed`，显式选择，不能用空 `modelId` 猜模式。
- `managedModelId`，托管模式必填；原生模式不使用托管模型 ID。
- `nativeModelOverride`，可空；值来自 CLI/适配器能力，不能拼装未验证参数。
- `cwd`、`permissionPolicy`、`extensionSelection`、`reasoningPolicy`。

建议解析结果记录：`runId`、`sessionId`、`generation`、Agent/适配器版本、
可执行文件来源、配置根、配置来源、配置修订指纹、模式、模型 ID/名称、
供应商、认证类型、代理路由标识、权限及扩展来源。结果不含可展示的密钥。
配置指纹只针对非秘密有效设置，不能把凭据哈希当公开诊断字段。

`generation` 区分一个聊天里前后两个子进程；旧进程的迟到事件不能更新
新进程的消息、忙碌状态、用量或“当前运行模型”。

托管方案在独立运行目录一次性生成配置，启动前写入成功才允许创建子进程。
模型切换创建新运行目录，不能改写另一个进程正在使用的文件。
Agent 级模板和默认设置用于以后启动的会话；编辑模板不热改运行中会话。

本地代理按 `runId` 对应的路由身份绑定确切 `modelId`、协议、上游和推理设置，
不再猜模型名或回退到 Agent 的第一个模型。每个代理凭据只允许该运行实例
访问其模型，且不等同上游 API Key；配置文件、argv、日志不能包含上游密钥。
运行中的路由固定到启动时的模型修订；更改供应商或密钥需要显式重连。
模型不可用、配置写入失败、代理路由缺失时，禁止偷偷使用其他模型。

RunJam 的模型绑定、模型默认项、原生模式下最近的选择分别保存。
切回原生只改变默认模式或当前会话模式，不能删除 `agent_models`。

## 6. “随时切换”的行为

Agent 设置页的模式切换修改“新会话默认值”，既有会话仍按已解析的方案运行。
会话工具栏（含宠物）的模式切换只作用于本聊天。允许同时存在原生会话和
托管会话，并允许多个托管会话使用不同供应商的同名模型。

会话切换过程：

1. 记录候选选择；如果正在回答，显示“停止回答并切换”与“回答后切换”。
2. 停止并结清当前回合、进行中的工具/审批；切换期间禁用发送与重复切换。
3. 校验新方案、认证和代理，启动候选进程并等待握手完成；握手前不发送推理。
4. 成功后提交本聊天新的运行方案/世代并清理旧进程；失败恢复旧方案，不让
   UI 提前显示切换成功。若旧进程无法恢复，明确显示需要重新连接。

CLI/ACP 原生会话 ID 与 RunJam 聊天 ID 分开保存。同一认证、供应商及配置
来源内，只有适配器已验证支持 resume 才恢复原生会话；否则新建 Agent 会话。
跨原生/托管模式默认新建 Agent 会话，保留 RunJam 中的可见历史。

切换界面提供“带上下文继续”与“从空上下文开始”；若更换供应商，先说明
选定的上下文会发送到目标供应商。带上下文继续发送可审阅的摘要和明确选择
的附件，不重放未完成工具调用、审批、认证信息或整段内部运行状态。
上下文交接不宣称完整恢复 Agent 内存，UI 需展示交接分界。

本机原生配置在外部改变：UI 可刷新来源/默认信息；已运行的会话显示
“原生配置已变更，重新连接后生效”，不自动中断。重新连接时重新解析。

## 7. 展示与扩展

Agent 页展示“新会话默认模式”“本机原生默认模型”“RunJam 已配置模型”。
历史 `.runjam-native` 移到“历史备份”，不能作为当前模型或当前配置来源。

会话页展示：模式、配置来源、认证方式、实际模型、连接状态。
启动方案表示“请求模型”；只有 Agent/适配器回报后才标记“已确认实际模型”。
无法取得真实模型时显示“请求模型，运行信息未确认”，禁止根据配置文件
直接标记“当前使用”。认证可显示 ChatGPT/API Key/未登录/未知；Pro 标签
仅在官方返回计划信息时显示，不能由模型名称推断。

原生模式默认不强制注入 RunJam MCP/技能/默认权限。用户显式选择额外项时
采用会话覆盖；与原生 MCP 同名时显示冲突并要求选择，不能静默覆盖。
技能部署记录 RunJam 所有权，项目中用户已有同名技能不能删除或覆盖。
适配器不支持会话级扩展时明确禁用该功能，不退回改写全局配置。

## 8. 迁移与实现边界

1. 有明确托管模型的存量会话继续托管；其他无法确定来源的会话要求选择模式，
   不由快照存在与否推断。首次上线时保留所有已绑定模型与旧历史文件。
2. 现有 `restore_native_config` 正常路径替换为模式选择 API；用户全局文件
   恢复/清理移到单独“修复旧版本配置”操作，只在用户明确选择后执行。
3. 原生实时读取不再优先历史快照；旧快照不自动删除，备份也不自动恢复。
4. 模型分配/取消分配/默认模型更改只更新 DB/模板；移除运行前后的共享写模型。
5. 先打通 Codex 的模式解析、隔离、路由与主/宠物会话切换，再扩展其他 Agent。
6. ACP 适配器能力必须按实际安装版本核验。系统 `codex` 版本不能证明
   `codex-acp` 内部使用的版本相同，诊断需同时记录这两者。

Codex 的账号状态/登录可由官方 app-server 提供（`account/read`、
`account/login/start`）；现有 ACP 没有相应能力时，用独立的账号探测层或
补齐适配器，不能编造 ACP 标准方法。深度 app-server 接入可后续演进，不
要求本次重写其他 Agent 的 ACP 通路。

## 9. 验收重点

- 模型管理、切模式、启动/关闭/卸载操作均不修改真实原生配置或清理原生认证。
  测试使用假 home；CLI 自身刷新认证/保存会话按原生模式契约允许。
- 同时运行原生、托管 A、托管 B；同名模型不同上游的请求不能串路由。
- 原生 ChatGPT 登录、原生 API Key、无登录、keyring、自定义原生根分别核验。
- `modelId` 不存在、写入失败、认证失败、握手失败时不发送到旧/默认模型。
- 更改托管默认值不影响正在回答的会话；推理开关与权限也不影响其他会话。
- 原生当前配置改变后 UI 更新；备份模型不得被标记成运行中实际模型。
- 主窗口与宠物使用同一解析/切换入口，覆盖打开、重连、恢复、停止中切换。
- 切换失败可回退，旧世代事件不能污染新世代，跨模式历史交接明确可见。
- 原生技能/MCP 被保留，项目同名技能不被覆盖；日志不含 Token/密钥/配置全文。

## 10. 官方依据

- [Codex 环境变量](https://learn.chatgpt.com/docs/config-file/environment-variables)：
  `CODEX_HOME` 不只隔离配置，还关联认证、日志、会话和技能。
- [认证与凭据存储](https://learn.chatgpt.com/docs/auth)：ChatGPT 登录与 API Key
  是不同认证路径；凭据可能存在文件或系统凭据存储，由 Codex 刷新 Token。
- [Codex app-server](https://learn.chatgpt.com/docs/app-server)：提供账号/计划信息、
  官方登录、模型和会话管理接口。具体可用方法按安装版本能力验证。

## 11. 第一阶段实现与边界

Codex 已提供原生/托管新会话默认值、主窗口与宠物的原生模型选项、会话独立
配置和带认证的代理路由、会话级推理与权限选择、握手失败保留旧客户端、
旧运行事件过滤及上下文交接选择。原生当前模型从实时文件读取，旧恢复入口
对 Codex 不再写文件或删除托管绑定。托管配置实际位于
`<RunJamData>/agent-config/runs/<runId>/codex`，模板仍可通过现有配置编辑器编辑。

运行信息记录请求模型、配置根、模式、ACP 会话 ID 和权限。真实模型及 Pro
计划信息尚未由官方账号接口独立确认，界面不宣称套餐已验证。
跨模式创建新 Agent 会话；选择继续时交接最近四条可见文本，而非完整工具
状态或完整 Agent 内存。原生模式暂不注入 RunJam 扩展，使用 CLI 自己的设置。
运行目录保留以供诊断；后续清理策略与完整原生 resume 不属于此阶段。

未用真实账号进行付费推理联调；自动化测试使用假配置目录和本机回环服务器。
